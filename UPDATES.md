# Glaze Music — how updates work

**Read this before touching anything release-related.** It is written to be handed to a fresh  
assistant with no context. Everything here was verified against the live system on 2026-11-06.

Supersedes `RELEASE.md` §0 (version control) and §4 (auto-update) — both are now historical.

---

## 1. The one-minute version

```
you push a tag  →  GitHub Actions builds on a Windows runner  →  publishes a release
                                                                        ↓
                                              installed app polls the release feed
                                                                        ↓
                                    sees a newer version → asks the user → installs on quit
```

Nothing is built on a developer machine. Nothing is uploaded by hand. The tag is the only input.

---

## 2. The parts

| Piece            | Where                                      | What it does                                                    |
| ---------------- | ------------------------------------------ | --------------------------------------------------------------- |
| Feed config      | `package.json` → `build.publish`           | `{ provider: "github", owner: "shami60", repo: "glaze-music" }` |
| Artifact name    | `package.json` → `build.nsis.artifactName` | `Glaze-Music-${version}.${ext}` — **must stay slugged**         |
| Client updater   | `electron/updater.cjs`                     | electron-updater wiring, state machine, IPC                     |
| CI               | `.github/workflows/ci.yml`                 | lint + logic checks + build on every push/PR                    |
| Release          | `.github/workflows/release.yml`            | on `v*` tag: build, upload, verify                              |
| Local feed check | `npm run verify:update`                    | validates `latest.yml` against files on disk                    |
| Hosted check     | `npm run verify:release`                   | validates the **published** release end to end                  |
| Notes            | `RELEASE-NOTES.md`                         | becomes the release body **and** `releaseNotes` in `latest.yml` |

### The three files that must exist on every release

```
Glaze-Music-<version>.exe            the installer
Glaze-Music-<version>.exe.blockmap   enables differential (small) updates
latest.yml                           the manifest the app reads
```

`latest.yml` is generated by electron-builder. **`--dir` builds do not produce it** — only a full NSIS  
build does. If you build with `--dir` and wonder why the feed is missing, that is why.

---

## 3. The rules — breaking any of these breaks updates silently

**1. The tag must equal the version.**  
Tag `v1.0.5` requires `"version": "1.0.5"` in `package.json`. The release workflow fails the build if  
they disagree, deliberately: the tag names the release, but `package.json` is what gets baked into the  
app and into `latest.yml`. Mismatch means the release advertises one version and installs another.

**2. Never rename the artifact without updating the workflow.**  
`artifactName` is `Glaze-Music-${version}.${ext}`. `release.yml` uploads by that exact path. It is  
slugged (dashes, no spaces) on purpose — see gotcha 1.

**3. Never publish a draft or a pre-release.**  
The client sets `allowPrerelease = false`, and drafts are invisible to the API. Either one makes the  
release undetectable. `verify:release` fails on both.

**4. Never delete an old release.**  
Users on 1.0.4 need 1.0.4's `latest.yml` and blockmap to compute a differential update. Deleting the  
previous release silently turns every update into a full 115 MB download — or breaks it.

**5. The repo must stay public.**  
The updater downloads anonymously. A private repo returns 404 to every installed client.

**6. Bump the version for every release.**  
electron-updater refuses to "downgrade". Publishing the same version again changes nothing for anyone  
already on it.

## 4. Shipping a release

```bash
# 1. edit package.json  ->  "version": "1.0.6"
# 2. edit RELEASE-NOTES.md  ->  "# What's new in 1.0.6"   (keep it short, it renders in a small box)
# 3. commit
git add -A && git commit -m "release: 1.0.6"

# 4. tag and push — this is what triggers everything
git tag -a v1.0.6 -m "Glaze Music 1.0.6"
git push origin main v1.0.6
```

That is the whole process. The workflow then:

1. fails if the tag ≠ `package.json` version
2. runs `npm run release` (vite build → electron-builder → stamp notes into `latest.yml`)
3. `gh release create` (or reuses an existing one), then `gh release upload --clobber` the three files
4. runs `node scripts/verify-hosted-release.mjs` against the **live** release

Step 4 is the safety net: if the upload is wrong, the build goes red instead of users finding out.

**Pushing a tag needs a token with `Contents: write`.** Releases themselves do not — the workflow uses  
the built-in `GITHUB_TOKEN`. A token that also touches `.github/workflows/*` additionally needs  
**Workflows: Read and write**.

## 5. Verifying

```bash
npm run verify:update     # local: latest.yml matches the files in dist-electron
npm run verify:release    # live: the published release is correct and downloadable
```

`verify:release` checks nine things and exits non-zero on any failure:

```
✓ release is published (not a draft)
✓ release is not a pre-release
✓ <exe> size matches the local build
✓ <blockmap> matches
✓ latest.yml matches
✓ latest.yml points at the uploaded asset
✓ sha512 matches the local installer
✓ feed version matches package.json
✓ host serves Range requests (206) — differential updates work
```

The Range check is not cosmetic. Without `206`, every update re-downloads the whole installer.

Run it with `RELEASE_DIR=...` if the build is somewhere other than `dist-electron`.

## 6. Gotchas we actually hit

**1. The provider switch renamed the file, and broke every update.**  
With `provider: "generic"` electron-builder writes the literal filename into `latest.yml`. With  
`provider: "github"` it **sanitises** it:

```
disk:        Glaze Music Version 1.0.4.exe     (spaces)
latest.yml:  Glaze-Music-Version-1.0.4.exe     (dashes)
```

The updater would request an asset that does not exist. `verify:update` caught it as  
`✗ missing artifact`. Fix: `nsis.artifactName` uses dashes. **Do not put spaces back.**

**2. `app-update.yml` is missing from `--dir` builds.**  
It is written by the NSIS target. An unpacked build has no feed config, so a packaged-but-unpacked app  
can never find updates. Test the installed build, not `win-unpacked`.

**3. The first update after a manual install is always a full download.**  
Differential updates patch the *cached copy of the old installer*. If the user installed by running the  
setup file themselves, the cache has no trustworthy base, the patched file fails its sha512, and the  
updater falls back to a full download. This is correct behaviour, not a bug:

```
Download block maps (old: v1.0.4, new: v1.0.5)
File has 673 changed blocks
Full: 118,084.67 KB, To download: 14,086.05 KB (12%)
sha512 checksum mismatch after differential download ... cached "installer.exe" is likely out of sync
Cannot download differentially, fallback to full download
```

After that update succeeds the cache holds a consistent pair, so the **next** update is small. Do not  
"fix" this by disabling differential.

**4. electron-builder cannot rebuild into a directory whose `app.asar` exists.**  
A read handle lingers on it (cause never identified — not Defender, not the indexer, and the Restart  
Manager API is unavailable because `Add-Type` is blocked). Symptom:

```
⨯ remove ...\resources\app.asar: The process cannot access the file because it is being used by another process.
```

Workarounds, in order: build with `--config.directories.output=<fresh-dir>`, or reboot. The same lock  
stops `Remove-Item` on the folder, but `SetLength(0)` through a write handle still frees the disk space.

**5. `.gitignore` must keep the `dist-*/` catch-all.**  
Build outputs are named by `--config.directories.output`, so new names appear without warning. Without  
the catch-all, `git add -A` commits hundreds of MB of binaries.

**6. `npm install` depends on `overrides` in `package.json`.**  
`discord-rpc` pulls `register-scheme` from a raw git URL; without the override, dedupe throws  
`Invalid Version:` and every install fails — including CI.

## 7. What the client does

Settings in `electron/updater.cjs`:

| Setting                | Value   | Why                                     |
| ---------------------- | ------- | --------------------------------------- |
| `autoDownload`         | `false` | Never downloads behind the user's back  |
| `autoInstallOnAppQuit` | `true`  | "Later" still installs on the next quit |
| `allowPrerelease`      | `false` | Pre-releases are never picked up        |
| `disableWebInstaller`  | `true`  | We only ship the full NSIS package      |

- First check **12 s** after launch, then every **4 hours**.
- Does nothing in dev (`app.isPackaged === false`).
- `GLAZE_UPDATE_URL` overrides the feed at runtime, for testing against a local server.
- Only a **manual** check surfaces an error; the background check fails silently by design.

**Where to look when it misbehaves:**

```
%APPDATA%\glaze-music\logs\main.log        grep "\[Update\]"
%LOCALAPPDATA%\glaze-music-updater\        installer.exe, current.blockmap, pending\
```

Useful log lines: `Found version …`, `Download block maps`, `Differential download`,  
`Cannot download differentially, fallback to full download`, `New version … has been downloaded`,  
`Update for version X is not available`.

## 8. Do not

- Do not upload release assets by hand — the workflow does it, and hand uploads drift.
- Do not publish a draft or pre-release.
- Do not delete old releases.
- Do not put spaces in `artifactName`.
- Do not change the `publish` provider without re-checking `latest.yml`'s `url` against the asset name.
- Do not assume signing is required for updates — **it is not**. An unsigned build updated itself  
  successfully on 2026-11-06. Signing affects SmartScreen warnings, not the update mechanism.
- Do not test updates from `npm run dev` — `app.isPackaged` is false there and the updater is inert.

## 10. If an update does not appear

Check in this order — each step eliminates half the problem:

1. **Is the app packaged?** `npm run dev` never updates. Use the installed build.


1. **Does the installed build point at GitHub?** Look at `resources/app-update.yml` inside the install  
   directory. It must say `provider: github`, `owner: shami60`, `repo: glaze-music`. A build made  
   before the provider switch points at `updates.glazemusic.com`, which does not exist.
2. **Is the release visible?** `npm run verify:release` — it fails on drafts, pre-releases and name  
   mismatches.
3. **Is the version actually newer?** The app ignores anything ≤ its own version.
4. **Read the log.** `grep "\[Update\]"` in `main.log` gives the exact reason, in plain English.
